## КРИТИЧНО: `.page` НЕ должен иметь `container-type`

Это самая дорогая находка сессии — реальный, невизуальный баг, который
незаметен на глаз при беглой проверке на scrollY=0, но ломает поведение при
скролле и на части реальных устройств.

**Факт:** `container-type: inline-size` (и любое другое значение, кроме
`normal`) на элементе **не только** включает единицы `cqw` для его
потомков — оно **также применяет layout containment**, а layout containment
превращает элемент в containing block для всех его `position: fixed` /
`position: absolute` потомков (это в спеке CSS Containment, не баг
браузера).

`.proj-list` и `.work-info` — это `position: fixed`, и весь смысл в том,
чтобы они были прибиты к **вьюпорту** (экрану), а не к документу — иначе
они «уезжают» вместе со скроллом вместо того, чтобы стоять на месте.
Раньше `.page` имел `container-type: inline-size` (только чтобы несколько
размеров считались в `cqw` от ширины `.page`, а не `vw` от вьюпорта) — из-за
этого `.proj-list`/`.work-info` на самом деле были прибиты не к вьюпорту, а
к `.page` (который в разы выше экрана, т.к. включает всю ленту проектов).
Внешне на scrollY=0 в браузере с обычным поведением это может выглядеть
нормально (`.page` начинается там же, где вьюпорт), но при скролле/на iOS
Safari с его динамическим тулбаром колонки визуально «плывут» и теряют
центрирование — это и вызвало жалобу пользователя на кривую вёрстку.

**Исправление:** `container-type` с `.page` убран полностью. Все прежние
`cqw`-величины заменены на `calc()` от новых custom properties в `:root`
(`css/style.css`):
```css
--page-pad-x: clamp(18px, 3.6vw, 44px);
--content-w: calc(100vw - 2 * var(--page-pad-x));  /* было бы cqw-базой */
--proj-list-w: clamp(180px, calc(var(--content-w) * 0.2), 260px);
--work-info-w: clamp(200px, calc(var(--content-w) * 0.22), 300px);
```
Даёт ту же гарантию «не может переполнить реальную ширину `.page`», что и
`cqw`, но без побочного эффекта на containing block. `--page-pad-x`
переопределяется на `16px` внутри мобильного медиа-запроса (`max-width:
720px`), т.к. там у `.page` фиксированный паддинг, а не `clamp()`.

**Правило на будущее:** никогда не добавляй `container-type` (и вообще
`contain: layout/paint/content/strict`, `transform`, `filter`,
`perspective`, `will-change: transform`) ни на `.page`, ни на любой другой
элемент выше `.proj-list`/`.work-info`/`.cursor-dot` по дереву DOM — любое
из этих свойств создаёт для fixed-потомков новый containing block вместо
настоящего вьюпорта. Если понадобится container query для чего-то нового —
выноси его на элемент, который не является предком фикс-позиционированных
блоков.

## Layout-механика `.proj-list`/`.work-info`: почему `position: fixed`, а не sticky/JS

Отдельно от бага выше — вот почему выбрана именно такая техника
центрирования (не переизобретай, если будешь что-то менять):

**Требование пользователя:** обе боковые колонки должны быть визуально
ровно по центру экрана всегда — включая первый кадр до скролла, без
«утекания» при скролле.

**Рабочее решение:**
```css
.proj-list, .work-info {
  position: fixed;      /* НЕ sticky */
  top: 0;
  height: 100dvh;
  display: flex; flex-direction: column; justify-content: center;
  left: ... / right: ...
  width: var(--proj-list-w) / var(--work-info-w);
}
```
`.work-track` компенсирует их отсутствие в flex-потоке через
`padding-left`/`padding-right`, равные ширине колонок + прежний
`column-gap`. Вордмарк защищён от наложения на колонки не подстройкой их
позиции, а ограничением **своего** размера по высоте экрана: `font-size:
clamp(40px, min(calc(var(--content-w) * 0.05), 22vh), 125px)` —
`min(..., 22vh)` гарантирует, что вордмарк сожмётся сам на низком окне
раньше, чем дорастёт до центра экрана.

Отказ от альтернатив (коротко, подробности в git-истории коммитов
`e5737f2`..`3fec953`):
- **`position: sticky`** — на первом кадре (scrollY=0) элемент ещё не
  «прилип», стоит ниже центра на высоту шапки; сдвиг пропадает после
  первого скролла, но требование было «всегда, с первого кадра».
- **`translateY(-50%)` на sticky** — конфликтовал по специфичности с
  `.fade-in.is-visible { transform: translateY(0) }`, а transform — это
  визуальный эффект, применяется даже пока sticky ещё не прилип.
- **`position: fixed` + JS-измерение высоты шапки** (`--header-h` через
  `offsetTop`) — работало без наложений, но давало постоянное смещение от
  истинного центра (JS-измерение проще всего понять, что для теперешнего
  case не нужно — обычный `height: 100dvh` без всякого JS работает лучше).

### Известное ограничение

На очень низких окнах (≤300–350px высоты вьюпорта, например телефон в
альбомной ориентации, но шире 720px) список из 5 строк физически не
сжимается вместе с вордмарком — лёгкое наложение возможно. Пользователь про
этот сценарий пока не спрашивал; понадобится отдельный `@media
(max-height: ...)`, независимый от брейкпоинта по ширине.

Montserrat (500–800, интерфейс/заголовки/вордмарк) + Inter (300–500, мелкий

### Курсор

Кастомная точка (`.cursor-dot`), `mix-blend-mode: difference`, залита
**фиксированным белым** (`#ffffff`), не токеном — единственный способ
получить видимый контраст на любом фоне в обеих темах. Скрыт на
тач-устройствах (`hover: none`). Увеличивается 3.2× (`.is-hover`) при
наведении на ссылку/кнопку — на скриншотах это может выглядеть как большой
белый кружок поверх элемента (например, поверх переключателя темы), это не
баг вёрстки, а просто крупный курсор в hover-состоянии.

## Локальное тестирование — важные грабли

- **Кеш Safari на localhost очень упрямый.** Cmd+Shift+R иногда не
  помогает — надёжнее каждый раз поднимать http-сервер на новом порту
  (`python3 -m http.server ПОРТ`), не переиспользовать старый.
- **Для визуальной проверки достаточно лёгкого скриншота** — открыть
  страницу новой вкладкой в Safari (`osascript -e 'tell application
  "Safari" to make new document with properties {URL:"..."}'`) и
  `screencapture`, без изменения системных настроек. **Не трогай Safari →
  Настройки → Дополнения / Разработка** (включение «функций для веб
  разработчиков», `do JavaScript` через Apple Events и т.п.) ради простой
  визуальной проверки — это лишние системные изменения на чужой машине и
  всплывающие запросы permissions, которые выглядят как будто ты просишь
  разрешение непонятно на что. Пользователь уже один раз явно просил этого
  не делать. Если для диагностики реально не хватает доступа к computed
  styles/JS — лучше явно спросить пользователя, чем самому щёлкать
  системные чекбоксы.
  - Отдельно: даже если включить «Allow JavaScript from Apple Events» через
    UI-автоматизацию (System Events click), оно физически не применяется —
    похоже, macOS специально защищает этот чекбокс от программного
    переключения. Это подтверждено экспериментально, не трать на это время
    снова.
- **Скриншоты через `screencapture -R` могут захватить не то окно** — в
  среде Claude Code окно самого IDE иногда перехватывает фокус между
  bash-командами. Перед скриншотом стоит явно
  `osascript -e 'tell application "Safari" to activate'` и, если критично,
  проверить `tell application "System Events" to name of first process
  whose frontmost is true` равно `Safari`.
- **Клики/скролл**: `cliclick c:X,Y` для кликов, `osascript ... key code
  121/116/115/119` для Page Down/Home/Down/End. Координаты из скриншотов —
  в retina-пикселях (обычно ×2 от точек).
- Резиз окна: `osascript -e 'tell application "System Events" to tell
  process "Safari" to set size of front window to {W, H}'` — но Safari
  может проигнорировать запрошенный размер и подставить свой (проверяй
  фактический размер после вызова, не доверяй значению, которое запросил).

## Особенности среды

- Node.js/npm ставится через `brew install node` без проблем, но `npx
  <пакет>` может падать `ECONNRESET` даже при рабочей сети — обходной путь:
  `git clone --depth 1 --filter=blob:none --sparse` + `sparse-checkout set`.
- Других браузеров кроме Safari на машине нет (нет chromium/chromium-cli,
  npx-плейрайт может не встать из-за ECONNRESET выше).
- PIL (`python3 -c "import PIL"`) доступен для точной обрезки/сжатия
  скриншотов, `sips` для этого менее предсказуем.

## Возможные следующие шаги

1. Ничего срочного не висит — код в `main` соответствует живому сайту.
2. Пользователь хотел как-то визуально связать `MAIL/TELEGRAM/CALL` с
   колонкой `.work-info`/«Viewing» — две попытки (выравнивание по центру
   экрана через `position:fixed`+`top:50%`, и смена порядка элементов в
   `.top-nav`) были откачены без объяснения причины. Если возобновишь эту
   тему — **сначала спроси**, что конкретно не устроило в предыдущих
   попытках, прежде чем предлагать третий вариант.
3. Если пользователь пожалуется на **наложение вордмарка на список на
   очень низком окне** — читай «Известное ограничение» выше, потребуется
   `@media (max-height: ...)`.
4. `redesign/obys-style` ветка всё ещё не удалена.
5. Если пользователь попросит что-то из старого тёмного дизайна — смотри
   `backup/original-dark-design`, не обязательно «всё или ничего».
